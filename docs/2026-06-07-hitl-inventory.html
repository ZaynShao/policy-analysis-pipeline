⑦ L1 源质量池 · 你让我定夺的三件事(我的判断)

✓ 独立成类:同意

这 4 个与 L1FeedbackQueue(#12)处理人、生命周期都不同——前者 builder 策展(源质量),后者 operator 报漏采(覆盖反馈)。按"不强行合并"原则应分开,确认独立为第 ⑦ 类。

轴1(已定):判定入口上衡观 — LLM 叙述层让判断可委派

builder-vs-operator 不是硬分线。LLM 把"为什么卡住"讲成人话(这是什么政策、核心摘要、卡在哪个判断点、字段什么意思)后,业务 / 其他参与者也能判,不必守后端;且前端常驻入口比"要手动跑的 CLI"更能防僵尸池。

前端 = 衡观(团队交付线下决定,2026-06-08 锁)。"哪个前端"叉子已收。L1 线注里"CLI/HTML 即可"读作"L1 不挑、听交互图",不与此冲突。

衡观侧待处理(阶段1):衡观面向运营,而这几个是 builder 池 → 需给它们一个"技术/builder 视图或角色",别与运营页混;builder-only 字段(如 #38 retry_params)在页面留 builder-only 编辑口。

两条护栏:① 个别决策仍 builder-only(如 #38 fetch 重试参数 = 选反爬策略,业务判不了);② OUT 不变:前端只做 IN,回灌走 dry-run→apply、记 reviewer/decided_run、经 poller。LLM 只讲不判、不进回灌(合 B6.1)。

适用边界:量小要判断的池(⑦ / 低置信,几十条)适合逐条对话;量大的(derives_from ~1200)宜批量 + 辅助检索 —— 按池选交互,共享"前端判 + poller 回灌"范式但池不合并。

合一 vs 分池:倾向「合一存储 + 分组消费」

一个 jsonl(带 kind 的统一契约、一个入池口),但审核界面按 4 个 kind 分区,每区给该 kind 专属 OUT 动作。理由:同处理人 → 别拆存储;但 4 个 kind 的回灌动作不同(入库 / promote / git mv / 重试),消费面必须分区,否则把 4 种决策混成一锅。属阶段1 交互图决定,先给 lean,Tier A+B 锁。

契约:IN + OUT 都到位(L1 已补 OUT 半)

IN:{kind, ref, reason, suggested_action, confidence, evidence}。OUT:{ref, kind, verdict, corrections?, reviewer, note, decided_run} + 每 kind 的 verdict→apply 动作表(见 ⑦ 各行 OUT 列)。基本覆盖我之前提的"缺 OUT 半"。

所有权划线(认同):L1 管【每 kind 的 verdict 语义 + 回灌 apply 动作】(只有 L1 知道能 apply 什么);B14 管【跨池标准信封 + 衡观交互/传输】,不碰 L1 的 kind 动作。

还差两小点(阶段1):显式 decided_at 时间戳(或并入 decided_run);幂等键(ref+kind+decided_run 去重)。过渡期沿用 oneshots(promote/sweep APPLY,自己重判、不读 verdict);正式 applier 等 L1 落盘 + B14 信封协议。
