一句话

③分析层要分成两条线:政策关系主线是主干,signal_context 是评论/市场信号辅线。两条线最后合成 analysis_context 给 ④读取。signal_context 可以先设计,但不能替代③整体设计。

③到底是什么

线回答的问题主要产物状态
政策关系主线 政策之间谁引用谁、谁依据谁、谁废止谁、国家政策怎么被地方落地。 relations/*.jsonl、反链页、关系摘要 旧产物存在但 stale,需要先审计再重生。

统一分析上下文 ④最终该读什么,而不是到处直接读 relations/signals。 analysis_context/*.jsonl 待设计后实现。

为什么不能直接实现完整③

当前 business_view 只有 50 个新流程产物。旧关系里的 derives_from、aligns_with、extends 很依赖主题、地区和业务归属;如果现在全量重生语义关系,会重复旧关系“归属未稳就连线”的问题。

正确先后顺序

  1. ③整体设计确认:当前步骤。
  2. ③-A 关系资产审计 preview:先盘点旧 relations 是否还可定位、哪些类型可信、哪些 stale。
  3. ③-B 高精度关系 preview:先做显式文号引用、依据、废止、细化。
  4. signal_context preview:使用已闭环的 171 条评论信号和 10 条市场信号。
  5. analysis_context preview:把政策关系和信号上下文合并成④输入。
  6. ③-C 语义关系 preview:等 ②-B 覆盖足够后再做国家到地方落地、对齐、扩展等语义关系。
  7. apply:每次都另行批准。

旧 relations 怎么处理

类别处理方式
高精度边: references / cites_basis / supersedes / clarifies可以作为候选和回归样本,但仍要在当前 raw/id/aliases 上重新 preview。
低可信语义边: derives_from / aligns_with / extends不能当事实复用;先降级为审计对象,等②归属稳定后重生。
iterates介于两者之间;有同机构同主题年度续作的强规则,但仍需 preview 验证。
_index_by_policy旧反链页随关系重生整文件重建,不手工修。

下一步真正要做什么

下一步不是写 signal_context 实现,而是做 ③-A 关系资产审计 preview: 只读旧 1_extracted/relations 和当前 0_raw/policies,输出中文 HTML 和机器 JSON,标出每条旧关系是否还能定位、是否 stale、是否可作为候选。

原则确认

  • 不写 raw
  • 不消费 review queue
  • 不把 blocked signals 当 accepted
  • 不直接复用旧 relations 当新事实
  • 不做 PID 补丁
  • 所有 apply 单独批准
