§1地基：源（source） vs 视图（view）

这是整套设计的根原则。项目里所有"孤岛 + 改来改去出废料"的病，根因都是把一个视图当成了源来维护。先把每样东西归类：

源 · SOURCE 持久 · 手编辑或确定性 · 唯一真理

  • L1 语料：政策/评论 raw + provenance（不可重抓，唯一不可逆资产）
  • canonical 词表：entities / themes / issuers registry
  • 分析框架（皇冠珠宝）：月报原型 · fact-check 规则 · 四维决策框架 · 打分体系 · LESSONS
  • 高精度确定性事实：supersedes / clarifies / cites_basis（504 边 ~100%）、date / region / issuer / 文号

视图 · VIEW 可重生 · 永不手修 · 永不打补丁

  • 推断关系图：derives_from / aligns_with / extends（语义判断）
  • 结晶页：themes 4 件套 / regions 区域页
  • 反链页：_index_by_policy/*
  • 查询索引：服务器侧 date×region×theme 结构化库 + 检索索引（见 §7）
  • L3 产出：月报 / 决策卡片（落盘 = 缓存，非真理）
铁律一：人只编辑"源"；"视图"一律由程序重生。出错时只能改源 / 改生成器 → 重生视图，永远不允许"手改视图 / 给视图打补丁"。这一条同时解决了：孤岛、迁移废料、以及本地↔服务器同步冲突（见 §7）。

§2两层骨架：归属层 / 分析层

同样是"源"，对每篇政策的处理要分两层——这决定了市级政策"存在但不进庞杂分析"，也决定了 API 的查询契约。

层对谁做内容成本
归属层
universal		 每篇必做（含市级） 挂 theme(s) + region(国/省/市) + date + 重要性。即政策"挂"在哪些主题、哪个区域下。这是 wiki 的链接骨架，也是 §7 API 的查询轴。 便宜
分析层
selective		 分级选择性做 关系网 / 业务影响 / 深度综合。只给值得的（国家级 / 省级 / 高重要性）。市级默认只"挂着"当成员，不强制吃这套。 贵
市级政策的归宿（你的点1）：一篇市级"虚拟电厂"政策，以成员身份出现在「虚拟电厂主题页」+「所属省页」的清单里——存在、可被检索、可被 API 查到，但不强制生成关系网/业务深析。顶层 schema 把"归属"设为必填、"分析"设为可选/分级，就框定了。

§3三条数据纪律

纪律 A · 采集只追加（L1）

L1 = append-only。多采城市 = 往库加不可变 raw 文件，永远不产生孤岛、不产生废料（入库时三维去重 + 新闻稿过滤就够健康）。所以 L1 的增量、持续滚动是对的、健康的——孤岛/废料从来不是采集的病。

纪律 B · 派生按"受影响文件"整文件重生（L2/L3）

新政策进来时：

✅ 正确：算出完整的受影响文件集（它挂的主题/区域页 + 它与已有政策产生关系的那些页），把这一集逐个整文件重生——某主题从 45 篇变 46 篇，就按 46 篇重渲染整页。
❌ 禁止：在旧文件里改个计数、append 一行、或跑个脚本去 remap 旧产物。这就是老路，会攒废料、留孤岛。"更新" ≡ "整文件重生"，不是 "edit in place"。

两个易错点（漏了会出现"漂移"——孤岛的弱化版）：

  • 一篇新政策不只影响它自己挂的页，还可能改变已有政策的页（如新政废止老政 → 老政页也要重生）。受影响集要算全。
  • 连边用 LLM 读语义，不是 regex 抓文号——这才是"明显相关但没明引文号"的 A-B / A-C 被连上、孤岛被解决的地方。

纪律 C · 定期全量重建做 GC

你有最高优先级 + 无限算力，正好用在这：按节奏（每月、或每次出月报前）全量重建一次派生层。即使周增量偶尔漏算了某个受影响文件，全量重跑会把漂移整体抹平。于是：周增量按文件重生（快）＋ 周期全量重建兜底（净）。

§4L2 的「零补丁」承诺（你的点2，写成物理形态）

对"L2 不达预期"，唯一合法的处置回路是：

改生成器 / 改源→ 整体重跑→ 过验收门？→ 通过 = 接受 不过 ↺ 回到第一步再重跑

绝不允许：发现错误 → 跑个小工具打补丁 → 补丁不奏效 → 原地继续打补丁。

让这个承诺可兑现而非靠自律，靠三个结构保证：

机制怎么保证
重建比补丁更便宜L2 做成一条幂等命令（temperature 0，输入=当前 L1，输出=整批受影响文件全替换）。无限算力下重跑很便宜 → "重跑"永远是最省选择，补丁诱惑从根上消失。
验收门先定、再建跑 L2 之前先定死客观判据：关系精度抽样 + 孤岛数 + 你给几对"明显该连"的政策做点检。重做循环对着这个门跑，不靠"感觉够不够好"。
硬规矩仓库里不允许出现任何针对 L2 输出的 oneshot / migration 脚本。一旦出现，即违约信号。

承诺的是这套纪律（整体重建·验收门·零补丁），不是"零错误"。但纪律到位，残余错误只会在下次重建里被整体修掉，永远不沉淀成废料。

§5为什么旧流程会"孤岛 + 废料"（给未来 session 看根因）

C 路径拆分后，干净 pipeline 只重写了 L1 采集 + audit + 清理 oneshot，L2 关系/结晶抽取器一个都没重建。后果：

  • vault 里那张图是化石——由拆分前的老脚本（_meta/scripts/oneshot_*）一次性产出，现工具链不能干净重生它。
  • 没有"活的连边器" → 每篇新政策天生是孤岛；A-B、A-C 没有任何工具去连。
  • 拆分后唯一动过关系的是给 id 漂移做的老边 remap = 搬化石 → 掉一地迁移废料，新增链接 = 0，孤岛全留着。

所以本设计的纪律 B（整文件重生 + LLM 语义连边）不是洁癖，是直接针对这个根因。

§6L1 覆盖策略

公司要求真覆盖，市级广度要做（推翻上一份评估里"停掉市级"的说法——那用了"市级=噪声"的论证，但业务约束优先）。落地节奏：

  • 现在批量 1-2 线城市 + 你标记的重点城市，批量做完。
  • 尾部 backlog 其余城市列成 todo，by 小时 / by 天 持续补——但必须做完，不是放弃。
  • 市级只走 §2 的归属层（挂主题+区域），不强制进分析层。既覆盖到、又不让庞杂分析膨胀。

§7消费架构：文件为源，Obsidian + API 双视图

心智转换：Obsidian 不是你的系统，文件才是。Obsidian 只是本地的"人类视图"。于是"迁移"不是"把 OB 搬上服务器"，而是"给同一批文件再开一个消费面（API）"。这正是 §1 source/view 纪律的延伸——几乎白送。

查询接口示例正是你要的：时间范围 × 地点范围 × 政策主题 → 命中政策集 + 评估。评估两档：有预算好的分析直接返回；任意 query 则让 LLM 现读这个切片 + 你的分析框架当场合成。

为什么几乎白送（复用已定的东西）

  • 查询轴 时间×地点×主题 = §2 的归属层。框一次，同时喂人类浏览 + 下游 API。这就是归属层要在顶层框死的原因——它是所有下游系统的接口契约。
  • 索引是视图 → 服从纪律 B/C，服务器侧零漂移、零废料。
  • source/view 分离让本地↔服务器同步变干净：人只编辑源（语料/词表/框架，git 同步），视图全由服务器重生，人手永不碰视图 → 永远不会有"人改"和"重生"打架的冲突。
  • 已有的 SCHEMA.md 顺势成为 API 数据契约，又是白赚。

§8落地顺序

清债（与设计无关，先减负）

删 ~/policy-analycsis 37MB 孤儿堆 + vault relations/_archive_*.jsonl 迁移残留；数据移出 git（LFS/外置）瘦身 159MB 历史；老 L2 图谱发生器 + 11 个 oneshot 归档、不复活。

把"源"固化为服务器上的真相源

L1 语料 + 504 确定性边 + canonical 词表 + 把分析框架（月报原型/fact-check/四维/打分）结构化成 agent 可调用的提示词/规则库。这是唯一要新"建"的脊柱。

L2 = 幂等重建命令 + 验收门点2 承诺的物理形态

先写验收门（精度抽样 + 孤岛数 + 你的点检对），再写"全局 LLM 语义连边 + 整文件重生"的幂等命令。这是第一块，因为它就是"零补丁"承诺的落地。

加索引 + API（§7 的 ②③）

解析归属层 → date×region×theme 结构化库 + 检索索引；薄 API 暴露查询。索引按纪律 B/C 重生。

L3 按需读最新 L2 + 框架产出

不系统化"依赖化石图的 L3"；做"LLM-over-语料、查询时连边"的产出。你已手验证过它能出活。
