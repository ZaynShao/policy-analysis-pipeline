一句话结论

你把两件事捆在一起了,但它们应该拆开:

  1. "rsync 不持久" — 这个有近乎免费的解,且与代码搬不搬无关。 实测:vault 本来就是个 git 仓、已有 GitHub remote(ZaynShao/energy-policy-analysis)。把 rsync 换成 服务器 git pull 即可——原子、带版本、带校验,今晚就能定。这是真正该做的durability 升级。
  2. "把 L1/L2 代码并进 hengguan 仓" — 这个我不推荐(至少现在不)。 它不解决 durability(数据流问题,代码搬不搬都在),却会把你高速迭代的 pipeline 押进前端团队的 PR/boundary 治理,还和 hengguan 的"模块走 API、不直连库"规则冲突(你现在是直写 heng-pg)。运维协同你已经拿到了——pipeline 早已作为容器跑在同一台服务器、同一 platform-net,这本就是"并部署不并仓"。

推荐路线: ① 立刻把 vault 同步从 rsync 换 git(Stage 1,低风险);② pipeline 保持独立仓 + 容器co-deploy,只把"schema↔sync 契约"加一道防漂移(Stage 2);③ "云端 24/7 产、本地只读阅览"是更大的独立阶段(Stage 3),到时再决定代码要不要更深耦合。"并仓"目前弊大于利。

3. 三个目标架构

架构 A — 最小 durability 修(rsync → git)推荐立刻做

Mac(产 vault + OB 阅览) ├─ git commit + push ──▶ GitHub: ZaynShao/energy-policy-analysis │ │ 东京服务器 ◀── git pull(定时/钩子)──────┘ └─ pipeline 容器(独立仓·platform-net)读 vault → run_sync → heng-pg → 前端
  • pipeline 保持独立仓;只把 vault 传输从 rsync 换成 git pull(原子/版本/校验,且 vault 本就在 commit 打 tag,顺手 push)。
  • 生成仍在 Mac。前端继续从 heng-pg 读。
  • 解决了:rsync 脆。没动:代码位置、生成位置。风险:几乎为零(基建已在)。

架构 B — pipeline 并入 hengguan monorepo(=你的提议)不推荐(现在)

safety-platform 仓 └─ services/policy-pipeline/(并入·Python 服务) 同 compose/PM2 部署 · 同 PR/boundary 治理 Mac 仍产 vault(经 git/rsync 上服务器)→ 容器读 → heng-pg
  • 真好处: ① 运维同栈(同 compose/PM2 管理);② schema↔sync 版本同仓耦合,根治 CONTRACT-REL-1 那类跨仓漂移;③ polyglot 先例已在,塞得进。
  • 真代价(为什么我劝缓):
    • 速度被治理拖死:你的 pipeline 是高速 solo(每天几十次 Codex 迭代);进 hengguan = 每次过 @gloriahao0909 的 PR-gate。前端团队的节奏 ≠ 你的节奏。
    • 耦合方向错:pipeline 天然耦合 vault(SCHEMA),不是前端。并进前端仓 = 把它和它真正的搭档(vault)拆开。
    • 撞 boundary 规则:"模块走 API 不直连库"——你现在直写 heng-pg,进仓后这点会被要求改成 NestJS API 写(=否决过的方案C,更慢、更绕)。
    • 不解决 durability:vault 还是单独的仓,代码并仓 ≠ 数据并仓。rsync 问题原样在。
  • 结论: 它给的"运维协同"你用架构 A/现有 co-deploy 已基本拿到;它独有的好处只有"版本耦合契约",而那个有更轻的拿法(见 §4)。所以现在弊大于利。

架构 C — 云端 24/7 产、本地只读阅览(你的长期愿景)下一个独立阶段

东京服务器(24/7 生产者) ├─ L1 采集(firecrawl·IP 无关 ✓)+ L2(②-B/③/projector)→ 写 vault(可写) ├─ run_sync → heng-pg → 前端 └─ vault git push ──▶ GitHub ──▶ Mac git pull → Obsidian 看最新(只读) 国内常驻节点(必须·微信地理风控) └─ wewe-rss + 评论 ingest → 写 commentaries → 并入 vault
  • 实现你说的"线上做完→本地 OB 最新":生成搬上云端,Mac 降级为只读阅览,靠 git pull 拿最新。
  • 可行性:L2 LLM(MiniMax/deepseek)东京 egress 已验✓;L1 走 firecrawl 与 IP 无关✓。
  • 两个硬问题:① RSS 必须留国内(微信),所以是"云端产政策 + 国内产评论"的双写 vault → 需按目录隔离的合并策略(政策/L2 在服务器写、评论在国内写,各管不同目录,git 按目录合并或分支合并);② 磁盘:云端跑全量生成 + 持 vault + .git 历史,4G 不够,需扩盘。
  • 这是个大阶段,不该和眼下的 durability/RSS 收口混。建议 RSS 收口后单开 brainstorming 立项。

4. 那"版本耦合契约"——并仓的唯一独有好处,有更轻的拿法

并仓真正独有的价值是:schema(Prisma 在 hengguan)和 sync(在 pipeline)同仓演进、一个 PR 落地,避免我们踩过的 CONTRACT-REL-1(跨仓字段名漂移、关系表静默 0 行)。但这个不必靠并仓换,有三档更轻的:

做法成本效果
A. 契约测试(pipeline 仓加一个测试:拿 hengguan 的 schema.prisma / 迁移 SQL 对账 sync 的列名映射)低漂移即测试红,CI 拦住。推荐
B. 版本钉死(sync 声明"吃 schema 版本 N",schema 变就 bump + 双侧对账清单)低显式契约,但靠纪律
C. 抽一个共享 contract 包(字段映射单一真源,两仓都引)中最强,但多一个发布物

所以:保持独立仓 + 一道契约测试,就拿到了并仓 90% 的收益,而没有治理/速度/边界的代价。

4.5 为什么"同机"不需要"并仓"(2026-06-08 问答固化)

常见误解:"如果 L1/L2 迟早跟 hengguan 跑在同一台机器上,那是不是必须把 pipeline 代码并进 hengguan 仓?否则同一系统上两个 repo 同时更新会乱。" —— 这里把两件互相独立的事当成一件了:

动作含义本设计的裁决
同机部署(co-deploy)L1/L2 的代码跑在同一台机器上(和 hengguan 容器并排)可以,本就如此已作为容器跑在同台、同 platform-net
并仓(monorepo)pipeline 的代码合进 hengguan 的 git 仓、走它的提交/治理流程不需要§3-B/§4 已否

"同机 ⇒ 必须并仓"这个因果不成立。

两个 git 仓在同一台机器上 = 完全正常、零冲突。 git 是按目录管的:
/root/policy-pipeline/ ← 自己的 .git,remote = ZaynShao/policy-analysis-pipeline /root/safety-platform/ ← 自己的 .git,remote = hengguan
两个目录、两套 .git、两个 remote、两套历史,文件系统层面互不知道对方存在。各自 git pull 各自的远端,根本碰不到一起——不存在"同时更新冲突"。这是任何服务器的常态(nginx 配置仓、应用仓、dotfiles 仓早就并存)。

真正需要协调的是"运行时契约",不是"代码仓":

共享资源契约(耦合点)
heng-pgrun_sync 写库必须符合 hengguan 的 Prisma schema(=列名对账教训 CONTRACT-REL-1)
vaultvault 目录格式是契约
docker 网络 safety-platform_platform-net两边 compose 各自引用同一 external network 即可并排跑

这些耦合无论代码在不在一个仓里都存在。并仓并不能让"schema 改了 run_sync 自动跟上"——该对账还得对账。所以正解是 §4 的契约测试守住 schema 这条线,而非并仓。

并仓唯一的真好处 vs 代价(诚实摊开):
  • 唯一真好处:一个 PR 能原子地同时改 schema + run_sync(消除"hengguan 改了列、pipeline 还没跟上"的窗口期)。
  • 代价:pipeline 整个被拖进 hengguan 的 PR-gate(过 @gloriahao0909、[DB-MIGRATION] 标、CODEOWNERS),且和边界规则"模块走 API"直接冲突(run_sync 直连库)。
  • 权衡:那个"原子跨切面改动"一年遇不上几次,契约测试 + 对账纪律足够覆盖;为它把整个 pipeline 塞进别人的 PR 闸门,不划算。
纠正前提: 架构 C 里 L1/L2 的 producer 是国内常开开发机,不是 Tokyo/hengguan 那台服务器(Tokyo 是消费端:run_sync→heng-pg→前端;且 WeChat/RSS token 须境内 IP,Tokyo 跑不了)。所以"L1/L2 搬到 hengguan 服务器"这个画面本身不会发生——它们搬去的是国内那台机,跟 hengguan 仓更是两码事。而 Stage 1 根本还没搬生成(只换 vault 传输 + run_sync 调度化),搬生成是后面的 C2/C3。

7. 风险与待澄清

  • 部署机制歧义(需向前端确认):仓内说裸机 PM2(滴滴 dev-container)是 prod,但东京服务器实测是 docker-compose。哪套是真?并仓的部署路径取决于此。
  • boundary "走 API 不直连库":当前直写 heng-pg 与此冲突;并仓会激化。不并仓则相安(我们是外部容器,边界对我们较松)。
  • GitHub 仓体积:vault .git 119M(OK);需确认无单文件 >100M(GitHub 推送硬限);markdown 仓基本不会有,稳。
  • git-vault 在服务器占盘:多 119M .git;4G 紧但够(可 --depth=1 浅克隆省盘)。
  • 双写 vault(仅 Stage 3):云端写政策/L2 + 国内写评论 → 必须目录隔离 + 合并策略,否则 git 冲突。
  • RSS 永远的例外:微信 token 不能离开国内 IP——无论哪个架构,评论采集都在国内节点,不进东京。
