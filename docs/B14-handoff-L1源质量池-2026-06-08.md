## 性质与区分(重要)

- **性质** = "缺陷/质量 + 策展"池。
- **处理人** = builder/技术(开发者/用户),**不是平台运营前线**。
  → 按你的轴1,这几个大概率 **CLI / HTML / 交互 session 即可,别上前端 UI**(请你定夺)。
- **与 `L1FeedbackQueue` 区分**:那个是覆盖漏采(operator / 前端驱动);这 4 个是源质量 / 策展
  (builder 驱动)。处理人和生命周期都不同 → 按你"不强行合并"原则,应是**独立的一类**。

## 4 个 L1 源质量池

### 1. L1 gate review_queue(低置信 政策/评论 分类)
- **IN 触发**:`policy_gate` 判 pass / commentary / reject 时低置信。
- **现状**:gate 有 `review_queue` action,但 orchestrator 只有 pass/commentary/reject 三桶,
  没有 review_queue 桶接(action 悬空)。L1 线会补桶。
- **OUT / 回灌**:人确认 → pass 入 `policies/` / commentary 入 `commentaries/` / reject 弃。

### 2. L1 discovery CHECKPOINT(候选渠道核验)
- **IN 触发**:渠道发现产候选(域名/机构核验没过,或 probe 偶失)。
- **现状**:ad-hoc oneshots(`discover_checkpoint_report.py` 出 triage HTML +
  `promote_checkpoint_channels.py` 提升)。L1 线会固化为可重复机制。
- **OUT / 回灌**:promote 候选 → 验证(进 backfill)/ drop。
- **注**:L1 线还会修核验门规则(host 省份校验),目的就是**减少进这个池的量**。

### 3. L1 sweep(存量误分类回扫:解读/问答 被误存为政策)
- **IN 触发**:存量 `policies/` 标题命中 commentary marker。
- **现状**:二元 DRY/APPLY(`sweep_existing_commentary.py`)。L1 线会改成路由进池 + 报数。
- **OUT / 回灌**:人确认 → git mv `policies/` ↔ `commentaries/`(§C 内确定性重分类)。

### 4. L1 fetch 失败池(反爬/正文过短站)
- **IN 触发**:列表页扫到 URL,但文章页抓取失败(反爬,或正文 < `MIN_BODY_LEN`)。
- **现状**:静默进 per-channel `ferr.txt`,无汇总。L1 线会改成汇总入池。
- **OUT / 回灌**:人定 重试(换抓取参数)/ 标 unfetchable / 弃。
- **实例**:河北省商务厅 `swt.hebei.gov.cn`,11 个真政策 URL(含 /zcfg/ /zcjd/)抓不下。

## L1 拟吐的契约(请你审/改)

```
jsonl 条目:
{
  kind: gate | checkpoint | sweep | fetch_fail,
  ref: channel / pid / url,
  reason: <为何进池>,
  suggested_action: <机器建议>,
  confidence: <0-1>,
  evidence: <标题/正文片段/probe 结果>
}
```

**开放问题(留给你定)**:这 4 个 kind 合一个 L1-builder 池文件,还是分池?
L1 倾向合一(同处理人=builder),但交互形态 / 分组听你的交互图。

## L1 OUT 契约(人审完 → 系统要的结果)

让池不是死投递。**L1 定每 kind 的裁决语义 + 回灌动作**(只有 L1 知道自己能 apply 什么);
**跨池标准化信封 + 交互/传输 = 你(B14)**。L1 现在**不建消费者**(回灌 applier),过渡用现有
oneshots(`promote_checkpoint` / `sweep APPLY`,自己重判/硬编码、不读 verdict);本节是
**文档化"将来正式回灌消费什么"**,给你一个可标准化的靶子。

| kind | 裁决 verdict | L1 回灌 apply 动作 | 附带字段 |
|---|---|---|---|
| gate | `pass` / `commentary` / `reject` | 暂存 ext 项 → `policies/` / `commentaries/` / 弃 | 可选 `corrected_label` |
| checkpoint | `promote` / `drop` | channel 候选→验证 / 移除候选 | — |
| sweep | `confirm` / `keep` | git mv `policies/`↔`commentaries/` / 不动 | — |
| fetch_fail | `retry` / `unfetchable` / `drop` | 重入抓取队列 / 标 unfetchable / 跳过 | 可选 `retry_params` |

**OUT 记录格式(L1 端,你之后包标准信封)**:
```
{ref, kind, verdict, corrections?, reviewer, note, decided_run}
```
处理人 = builder/技术 → 大概率 CLI/HTML 即可,听你交互图定夺。

## 时序与纪律

- **时序**:你的提示词写"等 L1 落盘再启动"。L1 线会先做**与池无关的那半**(核验门规则、
  抓取重试+可见性、SOP、backlog),池子那半(IN 路由 / OUT 回灌 / 契约)**等你盘完协议再接**。
  现在(你盘点阶段)先把这 4 个池加进清单即可。
- **纪律对齐**:L1 线遵守 §C(LLM 判定不写 raw)+ dry-run before apply,与你的核心原则一致。
- **过渡期**:在 B14 协议落地前,现有 oneshots + 二元 sweep + ferr 照常能用,不阻塞 L1。
