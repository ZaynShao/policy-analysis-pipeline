衡观生产部署 handoff

一次生产部署，把 pipeline 政策数据 + 通知铃铛 + L1 源质量审核页 同时点亮 · 2026-06-08
一句话
衡观团队 把 master 最新代码 + schema 部署到生产（含 db push）→ 完成后告诉 pipeline 侧 → pipeline 侧做数据灌入（run_sync）。两步接力，本文写清各自的活、确切命令、数据安全和回滚锚。

一、为什么需要这次部署（现状诊断）

排查生产库 hengguan 时发现：它的 schema 落后于已合并的代码，且不是迁移管理的活系统。具体：

诊断项生产实测影响
Policy 的 pipeline 列（pipelinePid 等）不存在pipeline 的 run_sync 写入会直接失败
_prisma_migrations 表不存在（db push 建的库，非 migrate）migrate deploy 跑不通（会重放 init 到已存在的表 → 报「表已存在」）
已合并入 master、但未上生产的迁移PR#14（pipeline 集成）、PR#16（通知）、PR#17（L1 页）三者均已合并代码已就绪，只差部署到生产
生产是否活系统是：Visit 163 · User 27 · Monthly 2 · Policy 50（demo）部署/清理必须 additive + 有回滚锚

对照：staging 库 hengguan_staging 已有 pipeline 列（也是 db push 加的）、已 sync 767 政策正常运行 —— 证明「生产照同法 db push 一次」即可补齐 schema。

关键纠正
cutover 的真正前置不是「PR#14 已合并」，而是「生产实际部署了这些代码 + schema」。生产从未部署过 PR#14，所以这一步必须先做 —— 而它正好和「让通知铃铛、L1 审核页在生产可见」是同一次部署。

二、衡观团队 要做的：生产部署

PR#14 / #16 / #17 均已合并入 master，代码已就绪——本节就是把它部署到生产。

  1. pg_dump 备份生产（回滚锚 #1，db push 前）。 
    pg_dump -Fc -d hengguan -f hengguan_predeploy_$(date +%s).dump
  2. 部署最新 master 的后端 + 前端代码到生产容器（走你们既有的 redeploy 流程）。前端含通知铃铛、L1 审核页（均 MANAGER 可见）。
  3. schema 跟上 = prisma db push（指向生产 DATABASE_URL，从 services/heng-guan/backend 跑）： 
    DATABASE_URL=<生产> npx prisma db push
    db push 会先打印将执行的变更，确认全是 additive（加列 / 加表）再 apply。它会补齐：Policy 的 pipeline 列、新表 PolicySemanticRelation / ManualEntryRequest / L1FeedbackQueue（PR#14）、Notification（PR#16）、L1ReviewQueue（PR#17）。不会删现有 50 政策 / 163 拜访 / 27 用户。
    为什么是 db push 不是 migrate deploy
    生产无 _prisma_migrations（db push 建的库）。直接 migrate deploy 会从头重放迁移、撞上已存在的表报错。db push 按当前库与 schema 的差异增量同步，与你们建 staging 同法，对纯追加变更安全。
  4. 完成后告知 pipeline 侧（这条最后一步）。然后进第三节。

三、pipeline 侧 接着做的：数据 cutover

列在这里让你知道接下来会发生什么；这一段由 pipeline 侧执行，不需要衡观团队动手。

  1. pg_dump 备份生产（回滚锚 #2，TRUNCATE 前）。
  2. 清 demo 政策：TRUNCATE "Policy" CASCADE; —— 删掉 50 条 demo 政策及其到政策的关联链（见下节量化）。163 拜访 / 27 用户 / 2 月报本体全部存活。
  3. 切换 run_sync 的 DATABASE_URL → 生产，跑全量 run_sync：灌入约 761 政策 + 998 语义关系（当前 vault 投影数，以 run_sync 实际为准）。
  4. 验收：核对生产 Policy 计数、抽查前端显示；异常则用回滚锚 pg_dump 还原。

四、数据安全 / 影响面（量化）

操作对现有数据
① db push加列 / 加表零删除，纯追加
② TRUNCATE Policy CASCADE 删：50 demo 政策 + 它们的关联 级联清空 PolicyTag / PolicyRelation / PolicyLocalDiff / BriefingPolicy(0) / MonthlyPolicy(4) / PolicySemanticRelation / _PolicyToVisit(6) / ManualEntryRequest
留：所有业务本体 163 拜访 · 27 用户 · 2 月报 · 全部机构 不受影响（多对多设计，TRUNCATE 只断「政策↔拜访/月报」的 6+4 个链，本体存活）
回滚锚（双保险）
pg_dump #1（db push 前）+ pg_dump #2（TRUNCATE 前）。任一步出问题都能 pg_restore 回到操作前。

关于那 6 个拜访链 / 4 个月报链：它们指向的是即将被删除的 demo 政策，断链是预期内的（demo 政策本就要换成真实数据）；真实政策入库后可重新关联。

五、完成后的效果

之前之后
政策数据50 条 demo约 761 条真实政策 + 998 语义关系
通知铃铛（MANAGER）无有，pipeline 同步失败会推消息
L1 源质量审核页（MANAGER）无有，人工裁决回灌 pipeline

六、衔接信号

衡观团队完成第二节（代码部署 + db push）后，回一句给 pipeline 侧即可。pipeline 侧随即执行第三节（数据 cutover），全程有 pg_dump 兜底。任何一步要中止都可立即停。

本文为生产部署衔接说明，由 pipeline 侧基于生产实测整理。命令中的生产 DATABASE_URL / 备份路径请以你们环境为准。
