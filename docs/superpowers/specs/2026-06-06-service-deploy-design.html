0 · 命名纪律

三层外壳只用名字：采 L1 → 加工 L2 → 取 L3。L2 内部阶段也用名字：源 · 归属 · 分析 · 结晶。代码里历史沿用的 ②-A/②-B/③-B/③-C 只是子任务代号，不是层。

  • 采 L1 = 八步采集法，append-only 抓取去重。产出 = 源（vault 0_raw/ 冻结真值），是采与加工的接缝。⚠ "源"是采的产出、不是加工的内脏；"采完没"和"加工建没建好"是两件事。
  • 加工 L2 = 归属 + 分析 + 结晶。幂等命令、temp0、整文件重生、不打补丁。
  • 取 L3 = 消费。本次只做"给前端供数据"，不做生成式产物。

依赖链：采 → 冻结源 → 归属(确定性身份→主题打分) → 分析(确定性关系→语义关系) → [结晶] → 取。

2 · 架构方案选型（已定 = 方案 B）

方案 B：Pipeline 独立仓 + sync 层直连 PostgreSQL。 Pipeline 留在自有仓（AGENTS/LESSONS 纪律完整），新增 scripts/sync/ 连 heng-guan PostgreSQL upsert。heng-guan schema 扩展走 safety-platform 仓 PR（附截图+前端该懂的描述）。

方案判定理由
A · pipeline 并入 safety-platform否决两套语言/规范混住，迁仓代价大
B · 独立仓 + sync 直连 DB采纳同 vault↔pipeline 解耦模式延伸，运维最简
C · sync 走 heng-guan 内部 API否决多端点+重试队列，比直连脆

3 · 服务器进程与目录结构

两个独立 systemd service，不互相依赖启动：

policy-pipeline-l1.service   ← L1 采集（初期手动触发，不挂 timer，待频率 TODO 闭环）
policy-pipeline-l2.service   ← oneshot，L1 完成后 ExecStartPost 触发，跑完自动 stop
  • L1 完成写 last_l1_run.json + l1_status: idle → 触发 L2 一次。
  • 日志走 journald；journalctl -u policy-pipeline-l2 -f 实时看。
  • L2 设 Restart=on-failure、TimeoutStartSec=infinity。Linux 不需 caffeinate，systemd 取代本地 nohup caffeinate。

4 · 增量策略 · L2 触发 · 队列 · 并发控制

4.1 增量派生（content-hash ledger）

state/hash_ledger.json 每 pid 存 raw_content_hash + pipeline_version。hash/version 未变 → 跳过用缓存；变了/新 pid/version bump → 重跑。每日只跑新增，存量接近零成本。

pipeline_version：重大代码变更（换 prompt/模型/评分逻辑）bump → 全量重跑；小修不 bump。与"整文件重生"纪律一致。

4.2 L2 触发：一次任务，不反复触发

触发信号是 "L1 完成事件"，不是"每篇政策入库事件"。无论 L1 这轮陆续抓进来多少篇，L2 只被唤醒一次，拿到整批 new_pids。
L1 启动 → 写 l1_status: running
  ├─ 政策陆续入库 0_raw/   ← 不触发 L2
  └─ 政策 N 入库            ← 不触发 L2
L1 结束 → last_l1_run.json{new_pids:[...]} → l1_status: idle
        → ExecStartPost 触发 L2 一次（唯一触发点）
              ↓ 整批 new_pids 写进 l2_queue（priority: normal）

4.3 单 worker + 显式队列

手动录入(high) ─┐
                ├─→ l2_queue.jsonl ─→ 单一 L2 worker（串行消费）
cron 触发(normal)┘
  • worker 单进程优先取 high（手动插队）。
  • 防 race：单 worker 串行写 ledger/vault，无并发写冲突；无多进程打 API → 无 429。

4.4 L1 run 不重叠

systemd oneshot 天然单例；cron tick 先读 l1_status，running 就跳过本次。等 L1 频率确定（§8 TODO）一起配死。

6 · Sync 层（pipeline → PostgreSQL）

scripts/sync/
├── run_sync.py        ← 入口，L2 ExecStartPost 触发
├── policy_mapper.py   ← vault YAML → Prisma Policy 字段
├── relation_mapper.py ← relations JSONL → PolicySemanticRelation
└── pg_writer.py       ← psycopg2 raw SQL, ON CONFLICT DO UPDATE
核心约束：
  • 只 upsert，不删除；不碰 pipelinePid IS NULL 的手动录入记录。
  • importanceOverride 有值时不覆盖 importance——人工改分不被 pipeline 重跑踩掉。
  • 完成写 last_sync_run.json {synced_count, skipped_override_count, errors[]}。
首次部署限制（诚实披露）：③-C 语义关系当前在 preview 阶段，vault relations 还没新数据；首次 sync 只写 ②-B 的 836 篇政策数据。③-C apply 完成后下次 sync 自动追上。

7 · 手动录入 · L1 漏采反馈 · 改分

7.1 手动录入：落 L1 收尾，触发 L2

落 L1 收尾（不是前置）：跳过发现/扫描(Step1-3)，从抓取+入库(Step4-5)进入，正常入库后自动触发这一篇的 L2。数据质量路径与自动采集一致。

用户提交 URL → 读 l1_status.json
  ├─ running → 进"待复核队列"，返回"采集进行中，稍后自动确认"
  └─ idle    → 查 vault 0_raw/（权威源，非 DB）
        ├─ 找到 → "已存在"
        └─ 没有 → L1 Step4 + L2 队列（high）
L1 完成(→idle)：扫待复核队列，重跑 vault dedup
  ├─ L1 已采到 → 通知"系统刚抓到，无需手动"
  └─ L1 未采到 → 自动触发 Step4 + L2
L2 已扫过该源但没抓到 → 记 L1FeedbackQueue（不影响主路径）
两条纪律：① dedup 查 vault 不查 DB（vault 真值，DB 可落后）；② l1_status 是唯一 L1 运行信号，不用进程存活判断。
